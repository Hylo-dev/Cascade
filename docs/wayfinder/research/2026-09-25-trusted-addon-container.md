# Trusted container that loads an addon after identification

Bounded research of 25 September 2026. Apple, Swift.org and public macOS 27 SDK sources; no native execution, launcher change, permission change or request to Apple. This document evaluates an alternative; it does not record an approved decision or a successful qualification.

## Outcome

**The composition is technically plausible and really moves the initial execution of addon code to after a controllable point.** Cascade launches its own isolated container; the container authenticates and waits; the supervisor records the observation of the process; only then does it authorize loading of the addon bundle. Even a hostile C/Objective-C initializer can thus start after registration. Dynamic loading does not create another process: the initializers run inside `dlopen`, before the call returns. [Apple, dynamic libraries](https://developer.apple.com/library/archive/documentation/DeveloperTools/Conceptual/DynamicLibraries/100-Articles/CreatingDynamicLibraries.html), [SDK `dlfcn.h`](</Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/usr/include/dlfcn.h:152>).

**It does not by itself resolve the current requirement on the whole managed process.** The startup window of the trusted container before identification remains. The policy in force explicitly includes that window too. The alternative reduces the portion in which addon code can intervene, but produces no kernel receipt from birth and does not prove cleanup of a container blocked before main. For embedded XPC there is a positive public lifetime contract tied to the client; it remains to be qualified that the entire composition satisfies the required proofs. [Apple XPC](https://developer.apple.com/documentation/xpc), [decision in force](../../superpowers/specs/2026-09-10-addon-control-policy.md), [decision of 20 September](../../../.scratch/cascade-product/issues/22-managed-process-exit-proof.md).

The cost is not a small replacement of the launch command: it requires a loadable format, an ABI between SDK and addon, attribution of the module's signature, controlled file access and a strategy for having distinct processes for distinct publishers. For the UI, the ExtensionKit container must also be qualified. It is not today a demonstrated shortcut for unblocking the gate.

## 1. Sequence that would have value

This is a proposal derived from the APIs, not an observed result:

1. The host launches an XPC service or an `.appex` **of the product**, containing only trusted code and dependencies.
2. The container opens the minimal protocol, demonstrates identity and current execution, then waits. The supervisor stays in a distinct process: after loading, the container's code is no longer a barrier against the addon.
3. The supervisor registers `EVFILT_PROC` with `NOTE_EXIT` and, for the requirement on executable change, `NOTE_EXEC`; it verifies the registration and reconfirms the same execution before releasing the load command. The monitoring must be owned by whoever must survive the container, not by the container itself. [SDK `sys/event.h`](</Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/usr/include/sys/event.h:248>).
4. A single package is verified and assigned to the session; the container receives exclusively the resources and grants of that session.
5. The container calls `Bundle.loadAndReturnError()` or `dlopen` and hands the entry points to its own SDK. A crash, a block during loading and later requests are now work inside the already observed process. [Bundle loading](https://developer.apple.com/documentation/foundation/bundle/loadandreturnerror()).
6. To disable, update or change trust domain, the entire container is terminated and its exit awaited; `dlclose` is not considered a safe ejection of the addon.

The boundary at step 3 is real only if **no** addon dependency is linked or loaded earlier. Even `Bundle.principalClass` implicitly loads code: it cannot be used as a harmless query of the manifest before observation. The package's identifiers and version must be read as data. [Apple `principalClass`](https://developer.apple.com/documentation/foundation/bundle/principalclass).

## 2. Embedded XPC and the ExtensionKit container are not interchangeable

| Variant | Documented part | Part to prove / limit |
| --- | --- | --- |
| `.xpc` service embedded in Cascade | Apple describes one process per client, launched on demand and terminated with the client. A later connection from the same client normally uses the existing instance. | It is not a public host of remote SwiftUI scenes. Multiple connections to the same name do not automatically create distinct processes per addon. |
| Trusted `.appex` embedded in Cascade | ExtensionKit hosts remote scenes; its process can provide a scene containing SwiftUI views. `AppExtensionProcess` can reuse an existing process. | It is plausible that the trusted scene shows views created by the module loaded later, but this specific composition with an external module, signing and sandbox is not qualified by the cited pages alone. |

Sources: [XPC](https://developer.apple.com/documentation/xpc), [`xpcservice.plist` manual, SDK](</Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/usr/share/man/man5/xpcservice.plist.5:17>), [AppExtensionProcess](https://developer.apple.com/documentation/extensionfoundation/appextensionprocess), [ExtensionKit UI](https://developer.apple.com/documentation/extensionkit/including-extension-based-ui-in-your-interface).

A single generic container identity is not enough to promise isolation for an arbitrary number of concurrent addons. The policy requires separate processes between publishers. Alternatives to design would be distinct embedded identities/finite slots, or a qualified topology with distinct clients; the documentation examined exposes no generic public “new isolated instance” option on `AppExtensionProcess`. Copying, renaming or re-signing wrappers inside the installed app is not an implicit solution: it would also modify the signed product. [Approved model, trust domain](../../superpowers/specs/2026-09-09-addon-runtime-design.md), [nested code signing](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html).

## 3. Signing by different publishers: possible, but in the expendable process

Hardened Runtime normally enables Library Validation: modules from Apple or with the same Team ID as the executable can be loaded. The public entitlement `com.apple.security.cs.disable-library-validation` is expressly intended for plugins signed by third-party developers. It would be granted **only** to the container that loads the addon, keeping Library Validation in the GUI and in the supervisor. It does not imply disabling App Sandbox or enabling JIT or unsigned executable memory. Gatekeeper applies additional checks when Library Validation is disabled. [Apple entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation).

Since macOS 14, library load constraints can restrict the accepted libraries even with that exception; they are signed into the executable and can express Team ID, signing identifier and hash. A publisher list built into the signature is useful for a fixed list, but it is not an ACL freely updatable from the manifest of an addon installed after distribution. Do not introduce a closed list of publishers as if it were already approved. [WWDC23, environment constraints](https://developer.apple.com/videos/play/wwdc2023/10266/), [definition](https://developer.apple.com/documentation/security/defining-launch-environment-and-library-constraints), [applying](https://developer.apple.com/documentation/security/applying-launch-environment-and-library-constraints).

The signature authenticated via XPC would become that of the **Cascade container**, not that of the plugin's author. The author/version/digest binding must therefore be established by still-trusted code before loading and kept in the supervisor. After `dlopen`, the process's replies are addon replies: the fact that the executable is signed by Cascade does not make the content of the messages trusted. This is a change of the authentication model compared with the `.appex` signed directly by the publisher.

Apple also describes plugin notarization and specifies that loaded plugins inherit the host process's entitlements rather than getting their own. The standard profile remains chosen by Cascade; an incompatible plugin must be rejected, not compensated for with a container that holds the union of all permissions requested by third parties. The practical availability of the entitlements on the `.appex` target, of external loading and of distribution with two publishers remains to be verified. [Notarization and plugins](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

## 4. Sandbox, storage and files changed after verification

`SecStaticCodeCheckValidity` verifies the signature, sealed resources and the supplied requirement, but Apple expressly warns that the check is safe only if the code is not modified concurrently; the result stays valid until it changes. The public flags allow checking all architectures, nested code and strict validation. A signature check followed by `dlopen` on a path that the addon can write or that can be replaced therefore does not close the TOCTOU problem. [Apple function](https://developer.apple.com/documentation/security/secstaticcodecheckvalidity(_:_:_:)), [flags](https://developer.apple.com/documentation/security/static-code-validation-flags).

A candidate solution must have one copy per verified version, outside the areas writable by the addon container, with effectively read-only access and updates that publish a new version without changing the loaded one. Dependencies, `@rpath`, symbolic links and resources must be included: not just the main Mach-O. The public loader `dlopen` receives a path and recursively loads the dependencies; it does not offer here a “verify this digest and map exactly those bytes” transaction. A hash in the name, `chmod` under the same UID or a second check are not on their own proof of the absence of concurrent writers. This is a design condition to satisfy, not an already implemented mechanism. [SDK `dlfcn.h`](</Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/usr/include/dlfcn.h:152>).

App Sandbox can assign different capabilities to an XPC service and to the main app; launching a helper directly with `Process`/fork/exec instead normally keeps the caller's sandbox capabilities. The container's concrete access to module and resources must be proven without granting it generic read/write access to Cascade's data. [Apple, sandbox and component separation](https://developer.apple.com/documentation/security/discovering-and-diagnosing-app-sandbox-violations).

A further cost of generic slots is persistent storage: if the same container is assigned at different times to different publishers, its container, credentials or leftover resources do not automatically become separated per publisher. The design must prevent this sharing or keep the data at a broker with per-addon grants; separation into successive processes alone is not enough.

## 5. Swift ABI and remote UI

Swift has a stable ABI on Apple platforms, but a binary SDK updated separately from its clients requires a library evolution and module stability contract. `BUILD_LIBRARY_FOR_DISTRIBUTION` enables these aspects; it does not authorize arbitrary ABI changes and does not make any plugin compatible with any version of the SDK or of a private framework. The current serialized XPC contract reduces this coupling; a plugin loaded in the container introduces an ABI boundary in the same address space. [Swift.org, author from Apple's compiler team](https://www.swift.org/blog/library-evolution/).

Minimal proposal: a versioned entry point and a shared SDK with controlled identity/version, avoiding incompatible static copies of the same SDK. The SwiftUI factory lives in the container and returns a view to the container; the GUI receives the scene through ExtensionKit. `AnyView` does not cross XPC and there is no need to make it serializable. A trusted scene can initially show an empty state and use the addon content only after the authorized loading: this is a composition to prove, not a certified example found in the sources. [PrimitiveAppExtensionScene](https://developer.apple.com/documentation/extensionkit/primitiveappextensionscene), [scene configuration](https://developer.apple.com/documentation/extensionkit/appextensionsceneconfiguration/init(_:configuration:)).

The basic process and scene APIs exist since macOS 13; the 14 minimum does not in itself require a raise. The new extension point definition macros from macOS 26 must not be confused with this availability: on 14 the legacy path must be kept and proven. [SDK ExtensionKit](</Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/ExtensionKit.framework/Versions/A/Modules/ExtensionKit.swiftmodule/arm64e-apple-macos.swiftinterface:84>), [SDK ExtensionFoundation](</Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/ExtensionFoundation.framework/Versions/A/Modules/ExtensionFoundation.swiftmodule/arm64e-apple-macos.swiftinterface:237>).

Do not design updates as a reliable unload/reload: the `dlclose` header says that a library may not be unloaded and cites, among the permanent cases, Objective-C classes or thread-local variables. The plugin's objects, callbacks and threads can in any case survive its return. The correct replacement for this architecture is a new process after verified exit of the previous one. [SDK `dlfcn.h`](</Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/usr/include/dlfcn.h:115>).

## 6. Executable change and control after loading

The normal design uses `dlopen`, not `exec`, so loading does not replace the container's executable. A native addon nonetheless remains capable of attempting process operations within the limits of the sandbox: an SDK rule forbidding it `exec` is not enough.

The `NOTE_EXEC` observation registered before loading is a public basis for detecting the replacement and revoking the session. `NSXPCConnection.setCodeSigningRequirement` is available since macOS 13 and invalidates the connection when new messages do not match the requirement; it must be set before activation. **Neither of the two is on its own a termination command or proof of exit.** Moreover, a replacement with code that satisfies the same requirement still requires management of the execution and of the session; Team ID does not mean execution identity. [SDK events](</Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/usr/include/sys/event.h:261>), [SDK Foundation](</Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/Foundation.framework/Versions/C/Headers/NSXPCConnection.h:153>).

The sources consulted do not specify a detailed lifetime guarantee for every hostile `exec` of an XPC service or an extension. The early observer makes this case testable after loading, but does not turn it into a documentation PASS. The identity confirmed before loading must not be reconstructed afterwards through a name/PID lookup. The approved global recovery remains a last resort, not a justification for restarting with unknown state.

## 7. What would change relative to the approved decisions

The [9 September design](../../superpowers/specs/2026-09-09-addon-runtime-design.md), section 8, speaks of an **initial preference** for a registrable container app; it keeps `.cascadeaddon` with an isolated executable as an alternative to test. The [distribution ticket](../../../.scratch/cascade-product/issues/05-extension-distribution.md) says to test the container before fixing the format. There is no immutable constraint to one external `.appex` per addon.

What stays closed, instead: no addon code in the GUI, distinct processes between publishers, initial Swift SDK, advanced remote scenes, profiles decided by the host, macOS 14 as the minimum to qualify, no exception for an orphaned managed process before main. The 24 September decision adds only emergency global recovery. The present alternative must respect them; it does not modify them implicitly.

The concrete choice to adopt it would be: **developers deliver a loadable module with the Cascade ABI; Cascade provides the process and the ExtensionKit scene that host it**, instead of entrusting each addon to its own external executable extension. This changes the developers' template and SDK, installation/discovery/enablement, process identity and distribution responsibility. The UI can remain remote SwiftUI and the publisher can keep the signature of its own module, but these advantages must be proven together.

A minimal separate probe makes sense without already adopting the format: a single container, a loadable bundle with an initializer that blocks after observation, a different signature when available, sandbox and out-of-process observation; then an ExtensionKit scene. The useful result must show control of the initializer and of the exit, and identify the residual limits of the trusted container. Before production adoption, concurrent isolation and storage between publishers, updates without TOCTOU and a macOS matrix are also required. If the current broker → external extension path meets these needs with fewer changes, it remains the least costly candidate; this document does not propose replacing it automatically.
