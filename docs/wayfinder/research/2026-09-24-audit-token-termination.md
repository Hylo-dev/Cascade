# Audit-token termination: public API and process identity qualification

**Verdict: the two libproc functions are a real identity-checked signaling mechanism, but do not qualify as a supported public-API solution for Cascade.** Their presence in the macOS 27 SDK is confirmed. The header explicitly warns that it contains private interfaces, Apple DTS reiterates that libproc lacks the stability/support contract of public APIs, and neither declaration supplies an availability annotation. In particular, a minimum of macOS 14.0 cannot be inferred. A public Mach audit trailer can supply an authentic sender token; it does not repair the termination API's support status or confer permission to signal a sandboxed peer.

Checked 24 September 2026. Read-only investigation of Apple documentation, Apple-published source and the installed SDK; only this report was written. No native fixture, process creation, signal, entitlement change, service registration or product-code change was performed. Existing research and scratch notes were context, not evidence. This report addresses stopping an identified broker; it does not establish automatic death coupling for arbitrary descendants.

## SDK presence is not a public support contract

The selected SDK is `/Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk`, version **27.0** in `SDKSettings.plist`. Its [`libproc.h`](</Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/usr/include/libproc.h:42>) has the private-interface warning at lines 42–45. Lines 132–135 declare the two audit-token functions and the two delegate functions without `API_AVAILABLE`. The local `usr/lib/libproc.tbd` exports both requested symbols. Header SHA-256: `246d87709fc6b9157ce5cf3c475656ac48e0e1ae8bbdc46cf45acd34294448cd`.

Apple DTS's July 2026 explanation is unusually direct: libproc's warning reserves the ability to change behavior without notice, unlike public API stability expectations; another DTS reply acknowledges its practical use while cautioning about compatibility. Thus **declared/exported and practically usable** is supported by evidence; **stable, supported public API** is not. No Apple exception or published API contract specifically promoting these two functions was found. [Apple DTS, “How is proc_listallpids supposed to be used?”](https://developer.apple.com/forums/thread/837541).

## What the implementation protects

In [XNU 10063.121.3 `proc_info.c`](https://github.com/apple-oss-distributions/xnu/blob/xnu-10063.121.3/bsd/kern/proc_info.c#L3276-L3378), the kernel copies the token, finds the process by its PID, holds a process reference, compares `pidversion`, checks signal authority, and signals that referenced process. A version mismatch or absent process produces `ESRCH`. The normal PID-reuse race between a userspace identity check and a later PID-only signal is therefore closed in that implementation. A token supplied as arbitrary bytes is not authenticated by this syscall: the caller must establish its origin separately.

The newer pinned [XNU 12377.1.9 path](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.1.9/bsd/kern/proc_info.c#L3322-L3506) first constructs an exact process identity, checks MAC policy without retaining the process, then reacquires and validates that identity before signaling. The delegate variants require `com.apple.private.delegate-signals`; the ordinary token variants do not use that entitlement. They still enforce caller and MAC permissions. There is no call to `task_for_pid` or debugger/get-task-allow requirement in this path. This is implementation evidence, not a guarantee that Cascade's exact App Sandbox profile authorizes the operation.

The matching [`kern_proc.c`](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.1.9/bsd/kern/kern_proc.c#L400-L509) verifies PID version when resolving the token; exact identity revalidation also compares the captured unique ID. [Process-reference handling](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.1.9/bsd/kern/kern_proc.c#L850-L940) and [exec reference draining](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.1.9/bsd/kern/kern_proc.c#L1005-L1074) prevent exec from crossing a held reference. Consequently, completed exec invalidates a previously captured execution token; a concurrent exec is serialized or rejected at revalidation, rather than silently authorizing a new image. Exit is not followed by a fresh PID-only lookup for signal delivery.

Apple's public [`ESMessage.h`](</Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/usr/include/EndpointSecurity/ESMessage.h:233>) explicitly distinguishes process PID from a program execution's `(pid, pidversion)` and states that exec updates the version. The [pinned exec implementation](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.1.9/bsd/kern/kern_exec.c#L6630-L6639) increments a finite integer counter and ensures it differs from the immediately preceding value. Do not promote this to a documented globally unique, forever-valid capability: an indefinitely retained token has no public non-repetition contract. Store it only for the authenticated live broker session and discard it on invalidation/restart; never refresh identity merely because a numeric PID still exists.

The functions are also different in an operationally important way. `proc_signal_with_audittoken` requests the specified signal; signal zero is rejected by the reviewed implementation. `proc_terminate_with_audittoken` implements sudden termination: it can choose **SIGTERM**, rather than unconditionally issuing SIGKILL. The [termination helper](https://github.com/apple-oss-distributions/xnu/blob/xnu-10063.121.3/bsd/kern/proc_info.c#L3181-L3214) sets policy and sends the selected signal. The [libproc wrappers](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.1.9/libsyscall/wrappers/libproc/libproc.c#L461-L488) return zero or an errno value directly; the termination wrapper writes the selected signal through `int *sig`. Neither successful return is an actual-exit receipt or a bounded exit guarantee.

Normal signal authorization is separate from code-signing identity. [`cansignal_nomac`](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.1.9/bsd/kern/kern_sig.c#L283-L355) evaluates sender/target credentials, root and special cases; MAC checks apply separately. Matching Team ID or passing a `SecRequirement` does not grant signal authority. Hardened Runtime need not be weakened for this source path, but existing sandbox/MAC refusals must be handled as failures, not bypassed.

## Obtaining an authentic token using public interfaces

**An existing XPC message:** the inspected public `xpc` headers expose no `xpc_dictionary_get_audit_token` or `xpc_connection_get_audit_token`. Do not redeclare either, use `dlsym`, or extract private object fields and describe that as public API. Apple Security's own implementation includes `<xpc/private.h>` and internally obtains an audit token; Apple's implementation privilege does not expose the helper to clients. [Apple `SecCode.cpp`](https://github.com/apple-oss-distributions/Security/blob/main/OSX/libsecurity_codesigning/lib/SecCode.cpp#L29-L35), [XPC-to-SecCode implementation](https://github.com/apple-oss-distributions/Security/blob/main/OSX/libsecurity_codesigning/lib/SecCode.cpp#L205-L225). This Security source is moving `main`, not evidence of the exact macOS 27 implementation.

The supported public operation is [`SecCodeCreateWithXPCMessage`](https://developer.apple.com/documentation/security/seccodecreatewithxpcmessage(_:_:_:)), followed by code-validity/requirement checking. Its [`SecCode.h` contract](</Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/Security.framework/Headers/SecCode.h:193>) creates a `SecCodeRef` using the message's associated audit token; it does not return the raw token. The inspected public Security headers provide no inverse token extractor or termination operation on that reference. `kSecGuestAttributeAudit` is an **input** selector, not an output accessor.

**NSXPC:** the public [`NSXPCConnection.h`](</Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/Foundation.framework/Headers/NSXPCConnection.h:134>) exposes PID, audit-session ID, EUID and EGID, but no full `auditToken` property or raw incoming `xpc_object_t`. The audit-session ID is not a process execution identity. Public `setCodeSigningRequirement:` is available from macOS 13, as is the listener requirement API with documented listener restrictions. Apple recommends these requirement facilities and the C-XPC Security bridge for their applicable versions. They authenticate code without exposing a reusable termination token. [Apple DTS, current XPC signature guidance](https://developer.apple.com/forums/thread/681053).

**A separately designed Mach exchange:** public [`mach/message.h`](</Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/usr/include/mach/message.h:525>) exposes `mach_msg_audit_trailer_t.msgh_audit` and the receive options `MACH_RCV_TRAILER_TYPE(MACH_MSG_TRAILER_FORMAT_0)` plus `MACH_RCV_TRAILER_ELEMENTS(MACH_RCV_TRAILER_AUDIT)`. Receive into a correctly sized buffer, find the trailer after the aligned message body, and validate trailer type/size before reading it. The [kernel initializes that trailer from the sending task's token](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.1.9/osfmk/ipc/ipc_kmsg.c#L485-L515). This supplies authenticated **Mach-message sender** identity. Token bytes in the application payload do not.

A C-XPC bootstrap can distribute a newly created Mach send right with public [`xpc_dictionary_set_mach_send`](https://developer.apple.com/documentation/xpc/xpc_dictionary_set_mach_send(_:_:_:)) and [`xpc_dictionary_copy_mach_send`](https://developer.apple.com/documentation/xpc/xpc_dictionary_copy_mach_send(_:_:)); both local declarations have macOS 10.7 availability. A broker can then send a nonce-bearing Mach handshake, whose received trailer identifies its actual sender. A token already received this way can be supplied as `CFData` under public `kSecGuestAttributeAudit` to `SecCodeCopyGuestWithAttributes`, then checked with `SecCodeCheckValidity`. This is a **composition candidate**, not an implemented or qualified Cascade protocol.

Its limits matter: the Mach sender must be authenticated and associated with the intended live broker before accepting work. A nonce or transferred send right alone does not prove that a Mach sender is the same execution instance as an earlier XPC sender; rights and messages can be relayed. No reviewed NSXPC/Security API establishes that cross-surface equality by extracting both tokens. A handshake that occurs only after startup also cannot identify or stop an already-hung broker that never completed it. Respect current Mach IPC restrictions; Apple recommends XPC over raw traps and documents additional requirements for enhanced-security processes. [Apple Mach IPC security restrictions](https://developer.apple.com/documentation/xcode/conforming-to-mach-ipc-security-restrictions).

## Operational consequence

Do not admit `proc_signal_with_audittoken` or `proc_terminate_with_audittoken` as the public termination primitive for the broker design. The source demonstrates a useful checked-identity mechanism; it does not satisfy the required supported-public-interface boundary, macOS 14.0 deployment contract, complete token acquisition path, sandbox authorization, or actual-exit evidence.

Do not replace it with `kill(pid, ...)` after a userspace check, manufacture a token from a PID, or introduce get-task-allow. Invalidation of an XPC connection likewise supplies no newly established force-exit guarantee here. Reopening this approach requires an explicit supported Apple contract (or a deliberate change to the public-API requirement), a fully authenticated session identity path, and qualification of permission/error/exit behavior under the unchanged signed profiles on the minimum supported OS. This finite investigation does not prove that no other macOS architecture can satisfy the broader product requirements.
