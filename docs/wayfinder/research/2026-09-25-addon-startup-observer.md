# Independent observer during startup of the `.appex`

Bounded research of 25 September 2026. Primary Apple/Clang sources and public macOS 27 SDK headers; cross-check of the local sandbox profile on macOS 27.0, build 26A5425a. No native probe run by this research, no change to product code, fixtures, entitlements or permissions. The updates distinguish the findings reported by the runner from the documentation conclusions.

## Outcome and scope

**Yes, the proposed protocol is adequate to identify and observe the specific controlled fixture while its `AppExtension.init` remains pending**, provided that the identification code runs before the deliberate block, that the kernel registration is confirmed and that the same instance answers a later challenge. This is a technical conclusion conditional on the invariants below, to be confirmed with the probe's receipts. It is not a general guarantee of authenticating hostile addons through a socket.

**This is not a full pre-main proof.** The first observable point arrives when the fixture has already run code inside `init`. It does not cover dyld, C/Objective-C initializers, the Swift runtime, nor a block earlier than the identification call. It does not retroactively identify an arbitrary `.appex` already blocked before that point. An absence of handshake does not allow concluding that the process does not exist or has exited.

The result can be called “pending startup after identification in the init” **only by demonstrating separately** that the host request `AppExtensionProcess(configuration:)` has not yet completed. The runner later found that the block in `AppExtension.init` does not satisfy this condition: see the update on the constructor below. The process APIs are available since macOS 13 in the [public SDK interface][ef-sdk]; the configuration exposes no early PID or audit token. The documentation says that the request launches or reuses a process and runs startup: the fixture's side transport must not be confused with the XPC channel obtainable through the returned object. [Apple, initializer](https://developer.apple.com/documentation/extensionfoundation/appextensionprocess/init(configuration:)-38zf).

### Important correction: `LOCAL_PEERTOKEN` is not a snapshot taken at connect

In the [Apple XNU 10002.1.13 source](https://github.com/apple-oss-distributions/xnu/blob/xnu-10002.1.13/bsd/kern/uipc_usrreq.c#L827-L857), `LOCAL_PEERTOKEN` reads `peerso->last_pid`, looks up that PID with `proc_find`, then reads the token of the current task. The path does not compare `last_upid`. The [current Apple source](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/uipc_usrreq.c#L859-L893) keeps this arrangement. It is therefore not correct to describe it as a token frozen at connect or a per-message credential.

The socket records the owner's PID and unique ID and can update this attribution when the user changes; see [`so_update_last_owner_locked` and socket initialization](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/uipc_socket.c#L373-L395). In addition, `exec` updates the process identity version in the [Apple source](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_exec.c#L6630-L6645). A previously read token, the current owner of the descriptor and the author of already buffered bytes are therefore not interchangeable.

The Security implementation accepts `CFData` of the exact size of `audit_token_t`, keeps its contents and uses that token in the process checks, rather than intentionally degrading to the PID alone. These are implementation findings, not APIs to call directly: [guest selection](https://github.com/apple-oss-distributions/Security/blob/main/OSX/libsecurity_codesigning/lib/cskernel.cpp#L66-L106), [token retention and check](https://github.com/apple-oss-distributions/Security/blob/main/OSX/libsecurity_codesigning/lib/csprocess.cpp#L34-L53).

For this probe, the requirement must identify **the fixture build prepared by the runner**: the expected signing identity and the CodeDirectory hash of the executed architecture, fixed before receiving input from the peer. Team ID or bundle identifier alone accept multiple programs/builds. The public `cdhash` grammar identifies a specific signed version. [Apple, requirement language](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/RequirementLang/RequirementLang.html#//apple_ref/doc/uid/TP40005929-CH4-SW16).

## Proposed sequence and fixture invariants

This sequence is a proposal deduced from the primitives, not a result already acquired:

1. The runner prepares and verifies the exact build. The observer, an independent process kept by the runner, creates the listener before requesting startup. Its lifetime and its logs do not depend on the broker or host that will be interrupted.
2. The fixture creates **inside `AppExtension.init`** a single new socket, with `FD_CLOEXEC`, and connects. No fork/exec, addon loading, transfer or sharing of the descriptor happens between creation and the block. These are invariants of the controlled code, not properties enforced by the signature or the transport.
3. The first frame declares the phase, an instance UUID generated in that init, and `getpid()`. The observer reads `LOCAL_PEERTOKEN`, verifies success and exact size, derives the PID from it and requires that it match the PID in the frame. The declared PID remains a consistency check, not the root of trust.
4. With the acquired token the observer creates a new `SecCodeRef` and applies the exact requirement; it then registers `EVFILT_PROC` on the PID with `EV_ADD | EV_ENABLE | EV_RECEIPT`, `NOTE_EXIT | NOTE_EXEC` and its own session identifier.
5. It accepts only the matching receipt, with `EV_ERROR` and `data == 0`. In this case `EV_ERROR` is the expected format of the positive receipt. A nonzero `errno`, a missing receipt or a wrong identifier stops the qualification. The manual explicitly describes these `EV_RECEIPT` semantics. [SDK `kqueue(2)`][receipt-sdk].
6. **After** the positive receipt, the observer generates a new unpredictable challenge. Before sending it, it reconfirms the full token and dynamic validation; it waits for a reply from the same socket with that challenge, the instance UUID and `getpid()`, still emitted inside the same init. It rereads the token and repeats dynamic validation after the reply. Every token must match the original one.
7. Only now does it record “instance observed during init” and allow injection of the planned fault. The fixture stays in the init; the runner keeps the independent evidence that `AppExtensionProcess(configuration:)` has not returned. After injection, the observer keeps the kqueue and records the raw events until the agreed deadline.

The challenge after registration rules out a reply prepared and buffered earlier being mistaken for proof of later liveness. The second attestation closes, under the fixture's invariants, the window between first identification and registration. A different token, an unexpected `NOTE_EXEC`, EOF or a challenge timeout produce **failed qualification/identity not established**, not an inference of exit.

`EVFILT_PROC` associates the note with the process resolved at registration: XNU stores `kn_proc` and inserts it into that process's list. A future reuse of the PID number does not transfer the note. The filter observes events after registration and does not recover an earlier exit. [Apple `filt_procattach`](https://github.com/apple-oss-distributions/xnu/blob/xnu-10002.1.13/bsd/kern/kern_event.c#L1002-L1056). Avoid `EV_ONESHOT` if you want to keep observing exit after a `NOTE_EXEC`. `NOTE_EXITSTATUS` is not needed; the probe requires the exit, not the additional authorization to read its status.

### PID reuse and the cost of an attack

The reasoning must not be “the PID will hardly be reused”. Before registration, a PID-based lookup can select another instance; a valid signature can belong to another execution of the same binary. The protocol instead enforces continuity of the non-delegated connection, a new challenge, and a full token equal on both sides of the registration.

For the fixture without FD transfer, the dead instance cannot answer the new challenge through a descriptor that only it owned. With hostile code capable of duplicating/transferring the descriptor, forwarding messages or alternating users, this inference does not hold: `getsockopt` does not certify the author of every frame. We do not quantify a minimum number of forks or seconds needed for an attack, nor do we treat `pidversion` as an infinite cryptographic nonce. Trying to qualify every adversarial interleaving empirically would cost far more than the present probe and would not turn the socket into a channel with a per-message audit trailer.

Even after a successful observation, `kill(pid, ...)` remains a different operation subject to PID reuse: the protocol does not create a public termination handle. For this investigation, termination and recovery keep the already authorized mechanism; the socket serves the evidence.

## Sandbox, pathname and permissions

**Local fact:** the system's [`application.sb` profile][sandbox-local] allows `network-bind` and `network-outbound` under the `resolving-subpath` of `application_container`, without conditioning that rule on `com.apple.security.network.client` or `.server`. This supports the attempt with AF_UNIX in the fixture's own container and without adding network entitlements. The file, however, explicitly declares itself a private interface subject to change: it is diagnostic evidence about the system examined, not an API to copy or a contract portable to macOS 14.

**More explicit public contract:** Apple documents UNIX-domain sockets in an App Group, even between sandboxed and non-sandboxed apps. A DTS answer confirms this possibility for `.appex`. This does not automatically prove the different pathname of the individual container used here. [App Groups Entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.application-groups), [Apple DTS](https://developer.apple.com/forums/thread/818192).

The non-sandboxed observer is nonetheless subject to the container protection introduced in Sonoma. Apple documents default access without a prompt for applications with the same Team ID, unless a more restrictive `NSDataAccessSecurityPolicy` applies. Signing the observer with the same team is therefore relevant; having the same UID or being ad-hoc signed does not by itself demonstrate that condition. [WWDC23, privacy, segment from 17:46](https://developer.apple.com/videos/play/wwdc2023/10053/?time=1066).

Pathname invariants for the probe:

- Resolve and record the fixture's actual container: the conventional pathname `~/Library/Containers/hylo.Cascade.AddonProbeContainer.Provider/Data/tmp` is a hypothesis to compare with what the sandboxed process sees. Do not assume that `NSTemporaryDirectory()` coincides with that directory.
- Verify that the actual directory and socket stay in the expected container, including resolution of any links, and that the listener is ready before startup. No alternative directory outside the container may be used silently to get around a denial.
- `sun_path` holds **104 bytes**, not 104 Unicode characters. With a NUL-terminated representation, accept at most 103 bytes of pathname. In the current home, the proposed directory is 82 UTF-8 bytes: that leaves 20 bytes for the basename beyond the slash. A full UUID as the name does not fit. A short name, with a collision handled as an error, is enough; the strong challenge lives in the protocol. [SDK `sys/un.h`][un-sdk].
- The pathname and the BSD modes reduce collisions and accidental access, but do not constitute authentication against every process with the same UID. The connected socket, the token and the requirement are the binding; a JSON or PID file left in the directory does not replace it. Do not remove a pre-existing pathname without verifying its type, its owner and that it belongs to your own probe.

There is no need to turn AF_UNIX into TCP loopback. The local network privacy described by Apple concerns operations on IP networks; it is not the reason to add a local network permission to this pathname probe. Any actual prompt or sandbox/container error must be recorded, not interpreted in advance as resolved. [TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).

## Only if this socket is not viable

If bind/connect or container access fail with the authorized profiles, the result is “side transport not available in this setup”, with syscall, error and OS recorded. Do not add sudo, Full Disk Access, temporary exceptions, permanent user permissions or network entitlements to make the probe pass.

A socket in an App Group is the minimal variant with explicit Apple documentation, **if the group is already shared and authorized**. Creating one changes the signed configuration and is not an implicit fix of the present experiment. If it is missing, it remains a separate candidate, not a solution already available within the current permissions.

A Mach message with an audit trailer authenticates the sender of the message and would be technically more precise than a socket's token. The public elements are `mach_msg_audit_trailer_t`, `MACH_RCV_TRAILER_TYPE` and `MACH_RCV_TRAILER_ELEMENTS(MACH_RCV_TRAILER_AUDIT)`; see [SDK `mach/message.h`][mach-sdk]. It remains indispensable to deliver a valid send right to the init through an already authorized channel. An arbitrary public name does not automatically create the sandbox authorization for the lookup. The ExtensionFoundation channel that arrives after startup cannot be used as an early bootstrap without contradicting the probe. With only the permissions described today, then, no smaller and already demonstrated Mach replacement emerges. The [previous research on audit tokens](2026-09-24-audit-token-termination.md) already distinguishes the public trailer from private XPC accessors.

## Update: socket preflight failed, before startup

The runner subsequently ran the preflight outside the tool's sandbox (`require_escalated`), without launching the extension. Build `probe-860_n5b0` failed with `bind-listen errno=1` in the [observer log](</Users/c4v4h/Library/Developer/Xcode/DerivedData/CascadeAddonRecoveryProbe/probe-860_n5b0/negative-observer.stderr>). Reading the signature confirms an arm64 Mach-O, Hardened Runtime, identifier `hylo.Cascade.AddonProbe.StartupObserver`, Team ID `A6A5HQL6K4`, with no associated Info.plist. This is neither a transport success nor a result on ExtensionFoundation lifetime.

For the same attempt, the runner reports a TCC chain with `responsible=com.openai.codex`, `accessing=hylo.Cascade.AddonProbe.StartupObserver` and a failure to locate the owning bundle `hylo.Cascade.AddonProbeContainer.Provider` with error `-10814`. These data support a container attribution/access problem; they do not by themselves demonstrate which of the two checks is the necessary cause of the denial. `EPERM` is compatible with MAC/sandbox and is not enough to diagnose a `sockaddr_un` error. The earlier “same Team ID” expectation therefore did not pass this concrete preflight.

Apple DTS explicitly distinguishes the signature of the accessing code from attribution to the responsible program, and describes heuristics for linking helpers and apps. The sources examined **do not promise that wrapping the same Mach-O in a `.app`, while still launching it directly from Python/exec, replaces the responsible Codex**. A main Mach-O and a correct Info.plist are packaging requirements, not a guarantee of a change of responsibility. The wrapper alone is therefore not a documented fix for this case; it was not tested here. [Apple DTS, On File System Permissions](https://developer.apple.com/forums/thread/678819).

### Diagnostic Mach variant with an exact exception

After this real block, a **separate probe with a different diagnostic profile** can be evaluated: add only `com.apple.security.temporary-exception.mach-lookup.global-name` with a single actual name, generated for the probe and embedded in the signed fixture. Apple publicly documents this entitlement and distinguishes lookup permission from registration permission. The non-sandboxed observer registers the service; the `.appex` keeps App Sandbox and obtains only that lookup. It is not a general authorization for Mach services, a TCC grant, or a change to the product profile. [Apple entitlement](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/AppSandboxTemporaryExceptionEntitlements.html).

The minimal variant can keep the observer as a child of the runner: allocate a receive right, create a send right from it and call the **public but deprecated** `bootstrap_register(bootstrap_port, name, port)`. The [current SDK](</Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/servers/bootstrap.h:72>) declares it deprecated since macOS 10.5. The [historical Apple header](https://github.com/apple-oss-distributions/launchd/blob/main/liblaunch/bootstrap.h#L213-L260) documents registration of a send right and rejection of a pre-existing active binding; it recommends launchd for well-known names and direct transfer of the send right for dynamic names. Here the early transfer does not yet have a channel, so the deprecated registration remains a bounded experiment, not a choice for the addon SDK.

Do not assume that any inherited bootstrap domain is visible to the `.appex`. Require successful registration, lookup from the fixture, messages with verified identity and no replacement of existing services. On collision or denial, the probe stops. Do not use `bootstrap_register2`, private flags or manipulation of the responsibility. The public name does not authenticate the process: authenticate every relevant message from its audit trailer.

The [historical Apple launchd](https://github.com/apple-oss-distributions/launchd/blob/main/src/core.c#L6697-L6720) removes dynamic services when the port dies; the [notification registration](https://github.com/apple-oss-distributions/launchd/blob/main/src/core.c#L6908-L6919) distinguishes `MACH_NOTIFY_DEAD_NAME` from managed services. For teardown, destroy the observer's receive right and release its own rights; then verify that the unique name is no longer resolvable. Do not turn the historical implementation into a promise about macOS 27 cleanup timing, nor attempt to remove any service belonging to someone else found under the same name.

If direct registration is not available in the required domain, what remains is the observer launched with a temporary user job, `MachServices` and `bootstrap_check_in`. This is the non-deprecated path explicitly described for MIG/raw Mach by the [SDK `launchd.plist` manual](</Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/share/man/man5/launchd.plist.5:633>). In this case too the report must record bootstrap/bootout and the absence of a leftover job: no permanent service is part of the result.

For the protocol, only the parts of [AuditProbe.c](../../../Prototypes/AddonPlatform/DirectV1/AuditProbe.c) that extract the aligned trailer and validate `SecCode` from the token are reusable. The sequence becomes authenticated HELLO → kqueue receipt → new challenge → ACK with a new trailer and an identical token, always inside the init. Keep the exact-build requirement; do not import the `exec` experiment or the artificial waits of the old fixture. Verify the trailer's size and type and reject unexpected messages. The additional Enhanced Security restrictions on Mach traps must still be respected if present in the actual profile; Hardened Runtime alone is not equivalent to those entitlements. [Apple, Mach IPC restrictions](https://developer.apple.com/documentation/xcode/conforming-to-mach-ipc-security-restrictions).

## Update: C constructor in the main Mach-O

**Finding reported by the runner:** in the Mach variant `probe-4g99x6ye`, `AppExtensionProcess(configuration:)` has already returned the process while the fixture's `AppExtension.init` is still blocked and the application channel is not ready. The authentic observation of the init remains useful, but does not demonstrate that the host initializer is pending. The later `STARTUP_PREMAIN` variant moves the observation point earlier, to a C constructor linked into the main Mach-O. This research evaluates its sources and limits; it does not certify the result of the new probe.

### Order actually supported by the sources

Clang documents `__attribute__((constructor))` for a `void` function with no arguments that runs before `main`. This is the compiler's contract, not a promise of being the process's first instruction. [Clang Attribute Reference](https://clang.llvm.org/docs/AttributeReference.html#constructor-destructor).

In the modern path of the Apple source, dyld runs `runAllInitializersForMain()` before returning the executable's entry point. The public `LC_MAIN` format contains the offset of the main executable's entry point. For the concrete build it must therefore be verified that the constructor is present in the initializer table and that the entry point path leads to `_NSExtensionMain`; the name of the C source or its mere compilation does not prove it. Both pointer-based (`S_MOD_INIT_FUNC_POINTERS`) and offset-based (`S_INIT_FUNC_OFFSETS`) Mach-O representations are admissible. [Apple dyldMain.cpp](https://github.com/apple-oss-distributions/dyld/blob/main/dyld/dyldMain.cpp#L903-L972), [SDK loader.h](</Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/mach-o/loader.h:524>), [SDK LC_MAIN](</Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/mach-o/loader.h:1609>).

The constructor must belong to the image loaded at startup, not to a library opened later by application code: Apple shows that the initializers of a dylib loaded with `dlopen` run during that call, which can happen after `main`. [Apple Dynamic Library Programming Topics](https://developer.apple.com/library/archive/documentation/DeveloperTools/Conceptual/DynamicLibraries/100-Articles/CreatingDynamicLibraries.html).

The order does not cover all initializers: dyld initializes libSystem first, then walks the dependencies, with distinct treatment for upward/delayed dependencies and inserted libraries. The path of each image notifies the Objective-C initializers before its ordinary initializers. A constructor priority does not demonstrate precedence over all this code; it is not needed for the proposed probe. [Apple DyldAPIs.cpp](https://github.com/apple-oss-distributions/dyld/blob/main/dyld/DyldAPIs.cpp#L3752-L3803), [Apple Loader.cpp](https://github.com/apple-oss-distributions/dyld/blob/main/dyld/Loader.cpp#L2486-L2553).

### Sandbox and identity during the constructor

Apple DTS confirms that the libSystem initializer includes App Sandbox setup for executables that enable it. The libSystem source shows the kernel, pthread and libc initializations, then secinit, before returning; dyld runs that initializer before the app's. These findings support using the main Mach-O constructor **after the normal sandbox setup**, keeping the same exact Mach exception. They do not authorize calls to the private initialization symbols, nor do they support a path that precedes or skips the sandbox. [Apple DTS, Reduce dyld overhead](https://developer.apple.com/forums/thread/813195), [Apple Libsystem/init.c](https://github.com/apple-oss-distributions/Libsystem/blob/main/init.c#L261-L316), [Apple DyldAPIs.cpp](https://github.com/apple-oss-distributions/dyld/blob/main/dyld/DyldAPIs.cpp#L3760-L3765).

The audit trailer does not depend on the existence of the Swift object: XNU copies the sending task's token into the trailer. `SecCodeCopyGuestWithAttributes` and `SecCodeCheckValidity` run in the already started observer, not in the stopped constructor of the `.appex`. It is therefore reasonable to repeat authenticated HELLO → kqueue receipt → challenge → authenticated ACK from the same instance. Actual Security success remains a precondition to be recorded, never to be replaced with the file signature or a declared PID. [Apple ipc_kmsg.c](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/ipc/ipc_kmsg.c#L491-L514), [SDK SecCode][seccode-sdk], [dynamic validation][validity-sdk].

**Limit of the attestation:** the trailer identifies the sender of the message; it does not certify its instruction pointer. The claim “still in the constructor” derives jointly from the authenticated exact build, the static presence of the initializer and the fixed protocol of the fixture that replies before returning. The UUID and deadline of the same instance must be kept when control continues in Swift; the release control must reach the application channel without creating a second wait in the init.

### What stays outside the probe

The correct descriptive name of the phase is **main Mach-O constructor, before the entry point**. `STARTUP_PREMAIN` can be the name of the variant, but it does not mean **full pre-main**: creation/exec → dyld → libSystem → earlier initializers → entry into the constructor remain outside, as does a block in the constructor before the handshake. The earlier step does not by itself guarantee that the host initializer is still pending: the runner must measure host request, handshake and application readiness separately in this variant too.

The `SIGALRM` guard starts only when it is armed in the constructor. `alarm(25)` schedules the signal from that moment, not from process creation, and replaces any existing alarm. Its handler must limit itself to async-signal-safe operations, for example `_exit`; it must not call Swift, CoreFoundation or logging with locks. Record the original deadline without implicitly rearming it on the move to the init. The timer is a diagnostic limit of the fixture and not a public guarantee of termination of any blocked process. [SDK alarm(3)](</Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/share/man/man3/alarm.3:47>), [SDK sigaction(2)](</Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/share/man/man2/sigaction.2:339>).

The Darwin sources consulted describe Apple implementations, but the `main` branch does not necessarily identify the binary version of the system under test; Apple DTS makes this limit explicit. They are not a new ExtensionFoundation contract for all macOS 14+ versions. Even a positive outcome remains evidence of the phase and build tested; it does not close the earlier window, does not qualify arbitrary addons and does not open the architectural gate.

## Evidence required in the probe report

Keep the exact build and requirements, actual entitlements, OS/SDK, resolved path, syscall errors, full token before/after, PID, instance UUID, nonce order, registration receipt, pending state of the host initializer, time of the fault, raw `NOTE_EXEC`/`NOTE_EXIT` and deadline. The observer must survive the interrupted process and shut down cleanly at the end of collection. Its remaining a child of the runner does not by itself confer any ownership over the observed process.

A `NOTE_EXIT` after a successful binding is evidence of the exit of the observed process; no event within a finite window is only a missed observation within that window. Neither an application callback nor EOF on the socket replaces this distinction. Even a positive result remains limited to the phase reached (init or main Mach-O constructor, to be stated explicitly) and to the macOS versions actually tested.
