# Lifetime probe before the provider's first instruction

Research of 25 September 2026. **Candidate to be qualified: suspended launch through the original launcher, identity acquired from outside without HELLO, and observation without a debugger during the measurement.** It is not a new ownership guarantee and does not admit the launcher: C0d stays blocked. This activity read documentation, manuals and headers; it did not run fixtures, attach, signals or launchctl mutations. The only artifact written is this note. The main task handles the relaunch of the app.

## The limit to resolve

The 15 PASS already archived prove the exit of the providers observed in `AppExtension.init`, in the C constructor and in the SIGTERM-resistant constructor. They do not prove the interval before the first diagnostic code: the observer identifies the target only after its HELLO. This is an observation gap, not a new observed case of an orphaned process. [Probe record](../../superpowers/verification/2026-09-25-addon-startup-observation.md).

Moving another callback earlier would move the limit. The new probe must instead obtain from the system the identity of the stopped provider, while root and broker launch it through the same path as before. Suspending it must not become a new lifetime mechanism in the product. The previous research already distinguishes suspension from ownership. [Spawn qualification](2026-09-24-spawn-managed-lifetime.md).

This makes it plausible to prepare an embedded XPC service while the host waits. **It does not demonstrate the mapping of the ExtensionFoundation provider**, which might have a dynamic service not present until the process request. `launchctl print` is explicitly declared non-API: it can help a diagnostic inspection, but its parsing must not become production API nor sufficient proof of identity. [Local launchctl manual](/usr/share/man/man1/launchctl.1).

## External identity without a debugger

An Apple DTS post proposes, for a child created suspended with `posix_spawn`, acquiring the task through `task_name_for_pid` and reading `TASK_AUDIT_TOKEN` with `task_info`. It also warns about the compatibility fragility of this composition. It is a useful primary source for the identification technique, **not a qualification of the ExtensionFoundation launch** nor a lifetime contract. [Apple DTS, thread 842442](https://developer.apple.com/forums/thread/842442).

The APIs are present in the selected public headers: [`task_name_for_pid`](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/mach/mach_traps.h:286), [`TASK_AUDIT_TOKEN`](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/mach/task_info.h:242) and [`task_info(task_name_t, …)`](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/mach/task.h:146). The declaration block in `mach_traps.h` is marked `Obsolete interfaces`; presence in the SDK does not remove the DTS warning.

Proposal to verify in the fixture: a discovered PID is only a candidate. Acquire the name port, read the kernel token, verify through Security the identity and CDHash of the exact build, register `EVFILT_PROC` with a receipt for EXIT/EXEC and reread the token from the same retained port before the trigger. Any error, identity change or exec makes the case not qualified. The protocol must be reviewed for races between these operations: no automatic equivalence between a PID read and an authenticated instance. The phase check must also attest the actual suspended launch; the absence of HELLO alone does not prove it. The Security check and the use of kqueue receipts reuse the existing observer. [Record](../../superpowers/verification/2026-09-25-addon-startup-observation.md).

A name port is a candidate for identity, not a termination handle: `task_terminate` requires a `task_t`, distinct from the `task_name_t` of `task_info`. Any debugger control port must therefore be qualified separately for cleanup only, and not inferred from the availability of the name port. [Public header `task.h`](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/mach/task.h:94).

## Why LLDB is not enough

Tracing changes signal handling: the debugger controls resumption or termination of the stopped process. In addition, the XNU parent-exit path treats traced children differently and can send them SIGKILL. A death observed with LLDB attached can therefore depend on tracing. It is not enough that LLDB attached to a process originally launched by the system. [Apple ptrace manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/ptrace.2.html), [XNU macOS 14, `kern_exit.c`, lines 2151–2232](https://github.com/apple-oss-distributions/xnu/blob/xnu-10002.1.13/bsd/kern/kern_exit.c#L2151-L2232).

The priority candidate avoids `ptrace`, breakpoints and debuggers in the lifetime window. If a debugger is needed to confirm the phase or prepare cleanup, that check must be kept separate and its residual effects verified; a PASS obtained under tracing does not become a PASS of the ordinary profile.

Apple documents that the debugging entitlement allows `task_for_pid` toward third-party apps with `get-task-allow`; a target without that consent remains protected. Xcode adds `get-task-allow` in debug builds and removes it before App Store distribution. So an authorized harness and a fixture with that entitlement would constitute a different diagnostic experiment, not a probe with unchanged signing. This source does not establish that the more limited `task_name_for_pid` has the same requirements: verify it separately. [Apple debugging tool entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.debugger).

## Two preflights before any fault

1. **Identity without HELLO, first on a cooperative fixture.** Use the current signing profile, keep entitlements and CDHash and verify name port → token → Security → kqueue receipt → unchanged token. The fixture can confirm the identity in a later check, without that HELLO being the source of the external identity. No suspended launch is needed for this first check. A denial does not authorize adding entitlements, disabling SIP or private APIs.
2. **Suspension and recovery with the original launch.** Establish whether a single invocation of the exact service can be configured before the `AppExtensionProcess` request, without a wrapper, a substituted program or a `kickstart` that changes the cause of the launch. Before injecting the loss of root/broker, a verified cleanup stably tied to the instance must exist; any control port must already be available and authenticated. The guard in the provider cannot arm itself if none of its instructions has run. Do not replace this condition with a kill on a discovered PID.

Only after both, measure natural death relative to the trigger while keeping the external observer alive, snapshot the result before any cleanup and distinguish exit, survival and insufficient observation. Do not let the debugger or the cleanup produce PASS. This is an experimental proposal, not a probe already carried out.

## Boundary that remains even with a PASS

The provider stopped before its first instruction and xpcproxy stopped before exec are different points. A PASS on the first would cover a point before the diagnostic code; it would not automatically demonstrate the entire interval from process creation, including any xpcproxy phase. The distinction follows from the different attach point documented for `launchctl attach -x`. [Local launchctl manual](/usr/share/man/man1/launchctl.1).

The next useful action is to qualify these two preflights, without changing the accepted policy. If they cannot be achieved with verifiable identity and cleanup, the lead remains not qualified. Neither a larger number of PASSes after HELLO nor a debugger with a different signature would resolve the remaining requirement. No contact with Apple, no gate change and no new native test in this research.

## Addendum: arming a second invocation of the original service

**The concrete lead is to reuse the job created by the first cooperative launch, keeping root and broker alive.** The [cooperative replacement already verified](../../superpowers/verification/2026-09-25-addon-broker-sessions.md) demonstrates two successive providers in the same broker; it does not by itself demonstrate persistence of the same launchd job. This latter condition must be established separately. The [`xpcservice.plist(5)`](/usr/share/man/man5/xpcservice.plist.5) manual describes a dynamic per-application namespace and relaunch of embedded services on a new request. This description justifies addressing the XPC broker from root, but does not document the namespace or the label of the ExtensionFoundation provider.

The [EF public interface of the selected SDK](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/ExtensionFoundation.framework/Versions/A/Modules/ExtensionFoundation.swiftmodule/arm64e-apple-macos.swiftinterface:238) exposes no operation to register the job in advance, nor its label: `Configuration` contains the extension's identity and the interruption callback. The [Apple initializer](https://developer.apple.com/documentation/extensionfoundation/appextensionprocess/init(configuration:)-2g0cy) directly launches or reuses the process. So these sources show no public point for pre-arming the first EF launch before the service is created.

Candidate procedure, **not run by this research**:

1. Complete the first cooperative launch. Diagnostically inspect the domain visible to root and the one visible to the broker with `launchctl print pid/<PID>`; identify the provider's actual service and its domain. Do not replace the observed label with the bundle identifier by analogy. Keep the snapshot, without turning it into a discovery API.
2. Have the provider exit cooperatively and wait for its kernel exit, leaving root and broker alive and without new requests. Verify that that very service stays registered and inactive. A vanished job or a new domain makes this lead inapplicable.
3. Only after qualifying recovery of the future suspended instance, arm that exact target with `launchctl debug <service-target> --start-suspended`, with no other options. The command modifies the next invocation; it does not cause it. Avoid `--program`, a substitute argument vector, `bootstrap`, `kickstart` and `attach`. [launchctl manual](/usr/share/man/man1/launchctl.1); local help `/bin/launchctl help debug`, reread read-only.
4. Send the second request through the same broker and `AppExtensionProcess(configuration:)`. Qualify the new kernel token and verify that the launch consumed the configuration on the same job. If EF creates a new label or UUID for the job, the earlier arming proves nothing about the new instance. The process must be the actual provider of the expected build, not xpcproxy; token, signature and suspended state require their own evidence.

**Permissions and limits to verify:** success of `print` does not prove permission for `debug`; the manual requires root for mutations of the `system` domain, but does not specify here the entire policy of the dynamic EF domain. Any denial must be preserved; it does not automatically authorize `sudo`, new entitlements or SIP changes. The name port remains insufficient to terminate the process. A `launchctl kill` on the label, like a kill on the PID, does not thereby become a stable handle to the specific incarnation. Cleanup must be qualified **before** arming a suspension that prevents the provider's guard from starting, and before any fault. If the experiment is abandoned after arming, the one-shot configuration left on the job must also be resolved and verified.

Even if it succeeds, this procedure would cover a later launch of the provider in the same broker. It would not automatically cover the first launch in the namespace, the job creation interval or the xpcproxy→provider transition. The exit78 gate and the accepted policy remain unchanged.

## Later proposal: disposable VM for lab cleanup

The main task completed two native preflights with the ordinary profile. The second run, `probe-veiyjfa3`, reconfirms external identity and complete cleanup. The `launchctl debug` request with only the variable `CASCADE_PROBE_DEBUG_PREFLIGHT=1` was refused with exit1 and the message `This subcommand requires root privileges: debug`. `--start-suspended` was not armed. [Local results](</Users/c4v4h/Library/Developer/Xcode/DerivedData/CascadeAddonRecoveryProbe/probe-veiyjfa3/external-results.json>). These are probes by the main task that came after the initial documentation research, not a suspended-launch probe.

**A dedicated macOS VM could provide cleanup external to the entire probe chain**, keeping the signing, Hardened Runtime and sandbox of the participants. Apple documents `VZVirtualMachine.stop(completionHandler:)` as a stop even from the `Paused` state, without giving the guest the chance to shut down cleanly. The operation can fail: its completion, final state and delegate information must be verified, rather than treating the sending of the command as proof of stop. [Apple API](https://developer.apple.com/documentation/virtualization/vzvirtualmachine/stop(completionhandler:)), [SDK header, stop contract](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/Virtualization.framework/Headers/VZVirtualMachine.h:235).

In the lab guest, an administrator account could run as root only the diagnostic `launchctl debug` command on the fixture's exact service; the chain's root process, broker and provider would remain normal users. The fixture's name “root” does not indicate Unix privileges. The VM manager and evidence collection would remain on the host Mac. Before suspending a provider, the stop of the chosen manager must be concretely qualified, including with a suspended guest; before the fault, the actual phase of the identified process must be proven. The absence of HELLO does not demonstrate that phase.

Tart is a lab candidate: the quick-start indicates an image to download of about 25 GB, initial settings of 2 CPUs and 4 GB RAM, and read-only directory shares through `:ro`. Only the fixture inputs would be exposed; the choice of the guest's macOS version would have to be recorded. [Tart documentation](https://tart.run/quick-start/). No VM is installed for this probe; the main task's survey found no VM runtime in the common paths. `df` reports about 5.9 GiB free on the internal disk: the choice asked of the user between about 60 GB available for the lab and an external volume is still pending. The 60 GB is an operational estimate, not an official Tart minimum.

Shutting down the VM would be **only cleanup after the measurement**: it does not prove that root or broker caused the provider's exit. The results must be acquired first, distinguishing natural death from survival. A probe in the guest does not eliminate the xpcproxy→provider interval, nor does it automatically transfer the result to other OSes or to the physical Mac. No loader pivot, weakened profile or gate change is implied by this proposal.
